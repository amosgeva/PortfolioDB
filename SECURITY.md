# Security

## Reporting a vulnerability

Use GitHub's private reporting: **Security → Report a vulnerability** on this
repository. That opens a channel only you and the maintainer can see. Please
don't open a public issue for anything exploitable.

Include what you'd want to receive: what you did, what happened, and why it
matters. A proof of concept helps.

This is a spare-time project, not a funded one. Expect a first reply within a
week or so, and no bug bounty. Fixes for anything that lets an attacker read or
alter someone's ledger take priority over everything else.

## What this software assumes about its environment

PortfolioDB is built to run on a machine you control. Since 1.8.0 **every port
`docker-compose.yml` publishes is bound to `127.0.0.1`** — the dashboard
(8501), Postgres (54320), the MCP (Model Context Protocol) server (8765) and
pgAdmin (58080) are reachable from the host itself and nowhere else until you
opt in. Consequences
worth stating plainly rather than treating as findings:

- **The dashboard's read-only views have no login, and its write pages share one
  password** (`PORTFOLIODB_DASHBOARD_PASSWORD`, generated by `make init`).
  Anyone who can reach port 8501 can see the ledger. Reaching it from another
  machine is a deliberate step — an SSH tunnel, a tailnet, an authenticating
  reverse proxy, or, last, an override that binds it to your local network —
  see [docs/exposure.md](docs/exposure.md).
- **The MCP server's bearer token is the main thing
  protecting it.** Its database role is read-only (`sql/create_ro_role.sql`),
  so the blast radius is limited to reading, but the token is a real
  credential: treat it like a password.
- **Containers run with as little as they need.** The app containers run as an
  unprivileged user with no Linux capabilities, `no-new-privileges` and a
  read-only root filesystem; Postgres keeps only the five capabilities its
  entrypoint needs. [docs/exposure.md](docs/exposure.md#what-the-containers-may-do)
  has the table.

Reports of the form "the dashboard has no login" are already documented above.
Reports that it can be reached *without* being deliberately exposed, that the
write-page password can be bypassed, that the MCP surface can write, or that the
token can be bypassed, are exactly what we want to hear about.

## Verifying the image you pulled

Every image `publish.yml` pushes to `ghcr.io/amosgeva/portfoliodb` is scanned
before it is pushed (Trivy; any fixable finding of high or critical severity
fails the publish), signed with [cosign](https://docs.sigstore.dev/) using the
workflow's GitHub-issued OpenID Connect (OIDC) identity, so no long-lived key
exists to leak, and carries a software bill of materials (SBOM) and SLSA build
provenance. To check that an image was built by this repository's publish
workflow:

```bash
cosign verify ghcr.io/amosgeva/portfoliodb:1 \
  --certificate-identity-regexp '^https://github\.com/amosgeva/PortfolioDB/\.github/workflows/publish\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

A tag can be moved; a digest cannot. To verify exactly what you run, resolve
the tag first and verify the digest (`docker buildx imagetools inspect
ghcr.io/amosgeva/portfoliodb:1` prints it), then pin `PORTFOLIODB_IMAGE` in
`.env` to `ghcr.io/amosgeva/portfoliodb@sha256:…`.

The build provenance is also recorded as a signed GitHub attestation (SLSA v1):
which workflow run built the image, the commit that workflow ran from, and the
commit the image was built from. Those two commits differ for the weekly
rebuild, which runs today's workflow against the release it republishes, so
the predicate lists both, named `workflow` and `source`:

```bash
gh attestation verify oci://ghcr.io/amosgeva/portfoliodb:1 --owner amosgeva --format json \
  | jq '.[].verificationResult.statement.predicate.buildDefinition.resolvedDependencies'
```

And the SBOM (SPDX) and BuildKit provenance ride in the image index:

```bash
docker buildx imagetools inspect ghcr.io/amosgeva/portfoliodb:1 --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/amosgeva/portfoliodb:1 --format '{{ json .Provenance }}'
```

Images published before 1.8.0 carry none of these; verification fails for them
by design.

## How the image is kept current

- **Pinned, then moved on purpose.** The Python base image, Postgres and pgAdmin
  are pinned by digest, the Python packages by exact version *and* sha256 hash
  (`app/requirements.lock`, installed with `--require-hashes`), and every
  GitHub Action — GitHub's own included — by commit. Dependabot proposes base-image digest
  refreshes, Postgres 16.x and pgAdmin updates, and action bumps as pull
  requests. It is configured not to propose a new Python minor or a Postgres
  major: those are migrations, done by hand in a release that says so.
- **Python packages** are not a Dependabot version-update ecosystem, because the
  lock is generated inside the image (`make lock`). They are watched by a weekly
  `pip-audit` of the exact lock, by the same audit on every pull request that
  touches it, and by GitHub's Dependabot alerts on the repository. An alert is
  answered with `make lock`, not by merging a bot's edit to the lock.
- **Weekly scans and rebuilds.** Every Monday `security-scan.yml` scans the
  published `latest` and `1` images (both architectures, by digest) as well as
  a fresh build of `main`; a failing scheduled scan opens a tracking issue that
  the next clean run closes. Every Sunday `publish.yml` rebuilds `latest` and
  the floating `X` / `X.Y` tags so Debian security fixes released since the last
  publish reach them. The schedule leaves the exact `X.Y.Z` tags alone: pin one
  and you get the bytes you pinned, and the responsibility for moving off it
  (unless a maintainer deliberately republishes that version and says so in the
  changelog).
- **The allowlist is short and dated.** `.trivyignore` holds the findings the
  scans may skip, each with its reason and a review-by date; once that date
  passes, every scan and every publish fails until the entry is re-checked.

## Secrets

Secrets live in `.env` at the repo root, which is gitignored, excluded from the
build context, and read only by server-side processes — the browser is served
rendered output, not the file. Runtime settings live in the database and are
editable from the dashboard; API keys and passwords deliberately are not,
because the dashboard has no authentication. The Settings page reports whether a
key is set, not what it is. If you find a path that leaks `.env` contents into a
response, a log line, or a container image, that is a vulnerability — please
report it.

## Supported versions

The latest `main` is what gets fixed. There are no maintained release branches.
The newest release's floating tags (`:1`, `:1.Y`) are rebuilt weekly for
operating-system fixes; older exact tags are not.
